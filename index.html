Tema 1

Lightning Network

Layer-2 de Bitcoin: dos partes bloquean BTC en un canal (2-of-2 on-chain), mueven balances off-chain con commitment txs firmados. La chain es para abrir, cerrar y disputas.

Capacity

BTC total locked. Tamaño del tubo.

Liquidity

Cómo está partido. ¿Puedes enviar o recibir?

Trampa clásica: canal grande ≠ puedes pagar a cualquiera. Importa la dirección.

Números — hazlos en papel

Alice↔Bob capacity 1,000,000 sats. Antes: Alice 700k / Bob 300k. Alice paga 50k.

Después: Alice 650k · Bob 350k · capacity igual. “Capacity didn’t change — only the split did.”

Merchant con canal de 5 BTC y local ≈ 0 tras muchos receives: inbound saturado. Pregunta la dirección antes de pathfinding.

HTLC + BOLT11

  • HTLC: pago condicionado (hash + time). El receiver revela el preimage o el timeout devuelve fondos. Atómico en multi-hop.
  • BOLT11: invoice con amount, payment hash, expiry, routing hints.
  • Unpaid: clock/expiry · amount vs hop · hint faltante · fee budget.

Fallos — misma UX, distinta causa

SíntomaCausaCheck
No routeHop sin liquidez / amountBalances, rutas, capacity
PendingHTLC in-flight, peer offlineTimeouts, liveness
No recibeSin inboundRebalance / LSP
Force-closeNodo offline, sin watchtowerAlways-online

Frase senior: “I’d separate routing failure from liquidity failure from peer liveness.”

Vocabulario que debes usar

HTLC · preimage · commitment tx · revocation / justice · watchtower · dual-funding · JIT · MPP · gossip · CLTV · jamming (tema abierto, no “resuelto”).

Di esto · Lightning 90s Lightning is a Bitcoin layer-2. Two parties lock BTC in a 2-of-2 channel, then update balances off-chain with signed commitment transactions. You get near-instant payments; on-chain is for open, close, and disputes. Multi-hop uses HTLCs so the payment is atomic: the receiver reveals a preimage, or timeouts refund. Capacity is the size of the pipe; liquidity is the direction. A huge channel can still fail if the split is wrong.
Di esto · no-route I’d reproduce with the payment hash. Check invoice expiry and amount first. Then: is this no-route, insufficient local outbound, or a peer timeout? Inspect local channels, then attempted paths and fee budget. Confirm whether we’re sender, forwarder, or receiver. I’d rather classify the failure than restart the node.

Tema 2

Settlement · PSP · custody

Payment = el usuario ve “enviado”. Settlement = el ledger del partner lo trata como final. La UI puede confirmar en 1s; finance espera un webhook idempotente keyed por payment hash.

Di esto Payment is the user-visible send. Settlement is when the partner’s system of record treats it as final. I’d ask what “final” means here — Lightning preimage, RGB state, or their ledger credit.

Por qué un PSP quiere USDT en Bitcoin

UX de stablecoin (USD, fees más predecibles) con rieles Lightning + ancla Bitcoin. On-chain BTC es lento/caro para micropagos. USDT clásico vive en Tron/ETH — otro trust y ops.

Preguntas de custody (semana 1)

  1. Who holds end-user keys today?
  2. Can anything freeze or reverse after preimage reveal?
  3. What’s disaster recovery for a force-close?
  4. System of record — your DB or chain proofs?

API = integras pagos. Cloud = ellos corren el RLN (no eres LN SRE).

Métricas de trial: success rate por clase de fallo, p95 invoice→settled, inbound headroom, webhook lag, force-close count.

Lightning moves value fast; RGB is how stablecoin state can live in a Bitcoin-native design. I haven’t shipped RGB to production. Caso 1 — Transfers API

REALTOKN · AWS SAM, Lambda, API Gateway, DynamoDB · Go/Python · crypto + RWA.

90s At REALTOKN I build the transfer backend for crypto and real-world asset moves. It’s serverless on AWS: API Gateway, Lambda, DynamoDB, packaged with SAM. I work in Go and Python. The hard part is not “call the chain” — it’s the state machine. A user can retry. A webhook can arrive twice. So I treat each transfer as a record with a clear status. Same discipline as a Lightning payments API: payment hash as the id, credit once, classify failures instead of saying “it failed.”
I key the transfer by a stable id. If the same request comes again, I return the existing record. I don’t create a second debit.

Caso 2 — MPC / custody

75s At REALTOKN I worked on MPC wallets. Instead of one private key on one server, the key is split. A transfer needs more than one share to sign. That reduces the blast radius if one machine is compromised. For Utexo I would ask: who holds end-user keys? Can anything freeze after a Lightning preimage? What’s recovery if a node force-closes? MPC is not an LN node seed — different blast radius — but the habit is the same: draw the custody boundary before you write the API.

Caso 3 — Liquid AMP (backup)

90s I integrated Liquid AMP at REALTOKN — Blockstream’s issuance tools on the Liquid Network. Liquid is a Bitcoin sidechain with a federation trust model, not a global ERC-20 contract. I have not shipped RGB to production. The question I know is: where does issuance trust sit, and where do payments sit? On Utexo, RGB is client-side validation, Lightning is the fast rail.
